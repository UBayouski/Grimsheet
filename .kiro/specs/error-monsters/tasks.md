# Implementation Plan: Error Monsters

**Note: `error-monsters` builds on the finished `grid-ui`, so `src/ui/` already holds `app.ts`, `render.ts`, `view-model.ts`, `types.ts`, `strings.ts`, `module.test.ts` and `src/styles/grid-ui.css`. No other spec needs to run first for this one to start. The Playwright flow runs against a self-contained fixture entry (`tests/fixtures/errors.html` with `errors-main.ts` and `errors.ts`), so it needs no real level. Only the final eye pass (task 4.2) needs `levels` task 5.1 done, because it looks at the real app, where `src/main.ts` imports `LEVELS` from `./levels/index`; `levels` 5.1 is complete, so the five real levels are already in the app.**

## Overview

The design uses TypeScript, so no implementation-language question is needed. The plan adds the error look on top of the finished `grid-ui` in four batches, from the pure core outward to the browser:

1. Batch 1 (IDE, sequential) moves `ERROR_CLASS` into a new pure module `src/ui/error-look.ts` and adds the ghost helpers, then extends the shared `types.ts` and `strings.ts`. These two tasks share `types.ts` and `strings.ts` and move `ERROR_CLASS`, so they run in order in the IDE.
2. Batch 2 (IDE, sequential) wires the pure core through the three browser files that build on each other: `view-model.ts`, then `render.ts`, then `app.ts` with its ghost state machine.
3. Batch 3 (Crew, parallel) adds the three disjoint deliverables that depend on Batch 2: the stylesheet, the e2e fixture, and the cross-spec `module.test.ts` and `main.ts` edits. Only task 3.3 edits `src/main.ts` and `tests/fixtures/main.ts`.
4. Batch 4 (IDE) adds the one Playwright flow, then the final eye pass and checkpoint.

Rules that apply to every task:

- Each task ends with the acceptance check `npm run verify` (`npm test`, then typecheck and lint). It stays green under `strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax` and `noUnusedLocals`. The one Playwright task (4.1) also needs `npm run e2e` to pass. The final eye pass (4.2) runs the checks it lists plus `npm run verify`.
- Each task lists its Files and its Tests. There are no optional tasks, so no `*` markers are used. There are no property tests in this spec (Decision D11): exhaustive example loops and fake-timer tests substitute for them.
- `error-look.ts` is pure and DOM-free: the Module_Scan scans it as `'pure'`, so it must not mention `document`, `window`, `Element`, `Event`, `navigator` or the other pure deny-list names (it types the media query as `MediaQueryLike`, with `() => void` listeners). `app.ts` stays scanned as `'dom'`, so it reads `doc.defaultView` and never the identifier `window`.
- No `eval`, `new Function`, `Math.random`, `Date.now`, `new Date`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `style` attribute write, `window` identifier or AI tool name other than Kiro appears in any new or changed `src/ui/` file (Requirement 8.6). The cause text reaches the DOM only through `setAttribute` (`title`) and `textContent` (the explanation and ghost note).
- Pure UI tests run in the Node environment. `render.test.ts`, `ghost.test.ts` and any other DOM test start with the docblock `// @vitest-environment happy-dom`. `error-look.test.ts` and `fixture-errors.test.ts` run in Node.
- Run mode: `[Crew]` tasks edit disjoint files and can run in parallel in Kiro Crew. `[IDE]` tasks share files or must run in sequence and run in the IDE.
- Single owners of shared files: `error-look.ts` and `error-look.test.ts` (1.1), `types.ts` and `strings.ts` and `strings.test.ts` (1.2), `view-model.ts` and `view-model.test.ts` (2.1), `render.ts` and `render.test.ts` (2.2), `app.ts` and `ghost.test.ts` (2.3), `src/styles/error-monsters.css` (3.1), the `tests/fixtures/errors*` files (3.2), and `src/ui/module.test.ts`, `src/main.ts` and `tests/fixtures/main.ts` (3.3). Task 3.3 is the **only** owner of `src/main.ts` and `tests/fixtures/main.ts`: task 3.1 only creates the CSS file and 3.2 only creates the fixture files, so the two CSS `import` lines are added by 3.3 alone and Batch 3 stays conflict-free.
